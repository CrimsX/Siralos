# Solaris security

This document describes the Solaris security model: how provider-driven capabilities are gated, how sandboxed processes are confined, and what is deliberately not implemented yet.

## Threat model

Solaris will eventually run development commands, tests, formatters, package managers, Git, and Godot processes on the user's machine. Those operations may execute untrusted repository code. The threat model assumes:

- The **repository being developed is untrusted** — its scripts and build steps may attempt to read, write, or exfiltrate anything the harness can reach.
- The **model provider is untrusted** — it may request arbitrary capabilities; every request is gated and enforced.
- The **user is trusted** but may misconfigure Solaris; defaults are conservative.
- The **host machine outside the configured workspace is sensitive** — credentials, SSH keys, browser profiles, and user documents must not be reachable from sandboxed processes.

The current implementation provides provider-accessible read-only inspection, the fail-closed workspace-mutation surface (the `workspace.create_file`/`workspace.edit_file`/`workspace.delete_file` tools and `/undo` exist but report `unavailable` before any write, approval, or checkpoint — Node offers no directory-relative (openat/renameat) primitive, so no approval for mutations is ever requested), the approval-gated sandboxed command surface (no command can execute at this stage — both runners fail closed as unavailable), sandboxed read-only Git inspection (unavailable at this stage: the adapter requires Solaris-owned private run directories, whose creation and cleanup fail closed because Node offers no directory-relative or delete-by-handle primitive), and project-independent Godot discovery and static project inspection (engine probing is intentionally unavailable at this stage); the security boundary described here governs all of them.

## Sandbox versus approvals

A permission decision determines whether Solaris permits an operation to proceed. A sandbox profile determines the technical restrictions under which it executes. Approval never means "run the command unrestricted" — at most it will mean "run the command using a broader predefined sandbox profile". Command execution is bound to the internal `validation-offline` profile regardless of the active user profile, so approval can never make command execution workspace-writable. No command can currently execute: both runners fail closed as unavailable.

## Fail closed

When the requested policy cannot be enforced the process does not run:

- No silent host-process fallback.
- No weakened profile.
- No network enablement.
- No fallback to an unrestricted backend.
- An actionable capability error is returned instead.

The sandbox backend reports `setup-required`, `dependency-missing`, `unsupported`, `degraded`, or `failed` states; none of them are treated as secure. Live conformance probes run only when the backend reports `available`, and an unavailable backend is reported loudly rather than passed as secure.

## Provider network separation

The model-provider adapter may contact its configured API endpoint from the Solaris host process. Sandboxed child processes never inherit that permission. All built-in sandbox profiles deny outbound network access (`network.outbound: deny`); there is no networked profile. Selecting any provider must never allow a child process to reach the internet.

## Credential isolation

Provider credentials and Solaris internal secrets stay in the provider adapter or host process. They must never be:

- added to child environments,
- written into sandbox configuration,
- included in command arguments,
- added to logs or application events,
- exposed through `/sandbox`, `/permissions`, or the sandbox doctor,
- sent to future tools,
- available to project scripts, Godot, or delegated agents.

Child environments are constructed from an explicit allowlist (`buildChildEnvironment` in `packages/adapters/src/environment/`); `process.env` is never forwarded verbatim. Variables matching `*_API_KEY`, `*_TOKEN`, `*_SECRET`, `*_PASSWORD`, `AWS_*`, `AZURE_*`, `GOOGLE_*`, `GITHUB_TOKEN`, `GH_TOKEN`, `SSH_AUTH_SOCK`, `NPM_TOKEN`, `NODE_AUTH_TOKEN`, `OPENROUTER_API_KEY`, `DEEPSEEK_API_KEY`, `OPENCODE_API_KEY`, `SOLARIS_CONFIG`, `NODE_OPTIONS`, `BASH_ENV`, `ENV`, `CDPATH`, `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_CONFIG*`, `NPM_CONFIG_USERCONFIG`, `NPM_CONFIG_SCRIPT_SHELL`, proxy variables (`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`), Godot editor-path overrides (`GODOT_EDITOR_PATH`, `GODOT4_EDITOR_PATH`), and dynamic-library/executable-loading injection variables (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `DYLD_*`) are denied, case-insensitively (Windows environment names are case-insensitive). Sandbox `HOME`/`USERPROFILE` and `TEMP`/`TMP`/`TMPDIR` are controlled by Solaris, and the sandbox wrapper's runtime-required environment is merged under the rules described in "Sandbox wrapper environment contract" below — the same deny patterns apply to wrapper-required variables, and Solaris-controlled values always win. Command environments additionally fix `NO_COLOR=1`, `FORCE_COLOR=0`, `TERM=dumb`, and `GIT_TERMINAL_PROMPT=0`, and the npm runner adds safe npm configuration (`NPM_CONFIG_IGNORE_SCRIPTS=true` disables pre/post hooks while the explicitly requested script still runs, plus audit/fund/update-notifier/color off) with the npm cache and user configuration pointed at sandbox-private run paths. The architecture check prohibits `process.env` inspection in package source.

## Built-in profiles

- **`inspect`** (default): workspace read-only, no writes, no process execution, no network. This is the profile under which the read-only workspace tools operate; write and process tools are not sent to the provider.
- **`develop-offline`**: workspace reads allowed, workspace writes require one-time approval, process execution requires one-time approval, network denied, minimal environment, protected metadata paths, timeouts, output limits, cancellation.
- **`validation-offline`** (internal, never user-selectable): the effective profile governing provider-accessible command execution. Workspace reads allowed, workspace writes denied, sandbox-private home/temp/npm-cache writable, network denied, minimal environment, closed stdin, process-tree confinement required. The active user profile may narrow command execution further, never broaden it. Notably, `develop-offline` permitting approved file edits does not make command execution workspace-writable.
- **`godot-probe-offline`** (internal, never user-selectable): the effective profile for project-independent engine probes (`--version`, `--help`, `--dump-extension-api`) when probing is available. Sandbox-private home/temp, network denied, minimal environment, closed stdin, confined process tree. The workspace is excluded from readable roots (`excludeWorkspaceRead`) and never writable: probes execute a verified private copy inside a Solaris-private run directory and never access the workspace. Engine probing is intentionally unavailable at this stage (the probe runner reports unavailable and never spawns the executable), so no probe currently runs under this profile.

There is no networked, unrestricted, or "full access" profile. No public configuration can set `process.execute` to unconditional `allow` in this milestone; a missing process rule fails closed.

## Why network is denied

No current Solaris operation needs outbound network from a sandboxed process. Provider API access happens in the host process. Denying network by default is the conservative baseline; a future profile that enables network would be a new, explicit, security-reviewed decision.

## Why project configuration cannot broaden access

Sandbox configuration is user-level only (`~/.solaris/config.json`). An untrusted repository must not be able to enable network access, add writable roots, select full access, disable environment filtering, change the backend, or disable protected paths. Project-specific restrictions may narrow user-level permissions later, never broaden them.

## Why Sandbox Runtime is an adapter

`@anthropic-ai/sandbox-runtime` (pinned exactly at `0.0.70`, Apache-2.0) is the first concrete OS-sandbox backend, isolated behind the core-owned `SandboxBackend` port. Core knows nothing about it; only the adapter module may import it (enforced by the architecture check). Its API is a beta research preview and may change; Solaris wraps all calls, normalizes its errors into `SandboxError` codes, and never exposes its configuration structures or command-string API through core.

## Platform support

- **Linux / WSL2**: Bubblewrap-based. The adapter reports missing dependencies (`bwrap` etc.) as `dependency-missing` and never disables AppArmor, changes sysctls, installs packages, or falls back to host execution.
- **macOS**: Seatbelt-based. Apple Events are never enabled; `open`/`osascript` escape behaviour is not allowed; network isolation is never weakened.
- **Windows**: The native backend is an **alpha** backend. It requires a one-time elevated setup (`npx sandbox-runtime windows-install`, one UAC prompt). Solaris detects incomplete setup, reports `setup-required` with the exact package-supported command, never runs the elevated install automatically, never triggers UAC, and never stores or inspects the sandbox account password. Setup and host-read capability are separate conditions: because the pinned runtime cannot express a reliable host-read allowlist on Windows (per-execution filesystem grants are unsupported, and ACL stamping cannot override inherited well-known-group read access), Solaris never reports the Windows backend as generally available — even when setup is complete it reports a degraded/unavailable state with the host-read capability explicitly false, and `process.run` and Git inspection are refused there (Godot probes are refused on every platform at this stage). No Windows execution is ever claimed verified; `npm run test:sandbox` on Windows skips loudly.

## Profile configuration lifecycle

The Sandbox Runtime manager is shared; Solaris never lets a later request execute under an earlier profile's configuration. Each request carries its own per-execution configuration covering the full effective filesystem and network policy (workspace read-only vs read-write, protected paths, the current run's private directory, the host-read allowlist), so a request can never inherit broader permissions from a previous profile. When the effective configuration of a session-level request changes, the manager is reset and reinitialized before use; the profile is only reported as active after initialization succeeds, and transitions are serialized with command execution.

## Protected paths

The `develop-offline` profile denies writes to `.git/`, `.solaris/`, `.env`, `.env.*`, `*.pem`, and `*.key` inside the workspace even though the workspace is writable. Protected-path matching folds case on Windows and macOS (macOS volumes are treated conservatively as case-insensitive), so `.GIT`, `.Git`, `.ENV` and equivalent variants cannot address protected paths; the fold applies during preparation and again immediately before mutation, including for new files whose final component does not yet exist. Windows junctions and reparse points cannot alias protected directories because mutation targets must resolve canonically inside the workspace. Environment filtering remains mandatory regardless; filename protection is defense in depth, not the primary safeguard. Where a backend cannot protect creation of a previously nonexistent matching file (a documented Windows glob-expansion limitation), that platform difference is documented and the backend's own behaviour governs.

## Environment filtering

See "Credential isolation" above. The allowlist keeps only variables required to run ordinary development tools (`PATH`, `SystemRoot`, `WINDIR`, `COMSPEC`, `PATHEXT`, `TEMP`, `TMP`, `TMPDIR`, `LANG`, `LC_ALL`, `TERM`), with sandbox-controlled home and temp values.

## Approved workspace mutations

> **Status note (fail-closed).** The mutation design below is **not offered at this stage**: every entry point of `workspace.create_file`, `workspace.edit_file`, `workspace.delete_file`, and `/undo` fails closed as `unavailable` before any write, approval, or checkpoint, because Node offers no directory-relative (openat/renameat) primitive and a same-user process can swap a parent or target at any instruction boundary. The tools are unavailable entry points; the retained layer is the core contracts, the reusable tested primitives, and the filesystem checkpoint store, while the former preview/approval/application machinery described below was largely deleted and is documented as future work; no approval for mutations is ever requested, and no new checkpoint is ever created at this stage (historical checkpoint data from earlier sessions, if any, may still be listed). This section documents the design for a future commit primitive that can mechanically bind the operation to the exact object.

Write tools (`workspace.create_file`, `workspace.edit_file`, `workspace.delete_file`) would run through the full stack: capability policy, a complete reviewable diff, one-time user approval, workspace path safety, protected-path enforcement, hash-based conflict detection, a serialized mutation lock, and post-write verification.

- Approval means **apply this exact prepared mutation once, bound to a digest of the immutable plan**. The approval request carries a SHA-256 digest over the plan (path, operation, before/after content hashes); `apply` verifies the plan it is asked to execute against that digest and refuses any mismatch. It never means future edits, process execution, network access, broader workspace roots, disabled protected paths, or another sandbox profile.
- Providers cannot approve their own actions, set approval defaults, hide diffs, modify policy, or retry a denied request without producing a new proposal that requires a new approval. An ordinary tool whose capability requires approval but that cannot produce a reviewable immutable plan is denied without execution (fail closed); approval is not inferred to apply to future tools.
- A mutation does not execute when: the policy denies it, the profile forbids writes, no reviewer is available, the user rejects, the reviewer times out, the reviewer's input reaches EOF, the reviewer throws, input is invalid, the target changed after preparation, a path is protected or escapes the workspace, a target or parent is a symbolic link, the file is unsupported, the preview is oversized, preconditions cannot be revalidated, the write fails, or post-write verification fails.
- `workspace.write` is `ask` under `develop-offline` and `deny` under `inspect`; under `inspect` write tools are not sent to the provider at all. There is no `autoApproveEdits` setting and no workspace-write `allow` option in the public configuration.
- Exact SHA-256 hashes are the conflict precondition; `workspace.read` returns the complete-file hash. Timestamps and file sizes are never conflict preconditions. Preconditions are revalidated immediately before the irreversible commit point, and every commit is identity-bound with an absence-preserving primitive: the target is first displaced to a same-directory quarantine (an atomic displacement of exactly the object at the target), the displaced object is hash-verified against the approved state, and the staged content is then committed with an exclusive hard link that atomically requires the destination to remain absent (fails on `EEXIST`) — a rename is never used for the commit or the rollback, so a target that appears after the quarantine displacement is never overwritten. Rollback restores the quarantined original with the same absence-preserving primitive; if a newer object occupies the target, the operation returns an explicit uncertain/conflict result that preserves both the quarantine and the later target and never reports success. The committed target is verified (type, bytes, hash, expected post-state) before the quarantine is released, and exclusive creation verifies every parent component's identity immediately before the open and proves the created object's identity (handle vs path) before any byte is written, so a parent swapped for a link is detected before any write and cleanup removes only the identity-proven object. A target or parent swapped after approval is therefore a `conflict` or `failed`/`uncertain` recovery, never an overwrite or delete of unapproved content. Where the filesystem cannot provide the absence-preserving primitive (hard links unsupported), the operation fails closed.
- Protected paths (`.git/`, `.solaris/`, `.env`, `.env.*`, `*.pem`, `*.key`, Solaris configuration, sandbox metadata, anything outside the workspace) cannot be overridden by approval or provider requests, are applied again immediately before mutation, and are matched case-insensitively on Windows and macOS (treated conservatively as case-insensitive), so `.GIT`, `.Git`, `.ENV` and equivalents cannot address protected paths. Windows junctions and reparse points are rejected through canonical containment.
- Mutations are serialized in-process; temp files use unpredictable names, stay in the target directory, are hidden from listings, and are cleaned up after success or failure. Cancellation before the commit section prevents mutation; once the irreversible commit point is reached, cancellation cannot interrupt verification and lifecycle finalization. Every replacement and every deletion first moves the target to a same-directory quarantine (an atomic displacement of exactly the object at the target), verifies the displaced object against the expected hash, and only then commits through the exclusive absence-preserving hard link — so a substituted or externally-changed target is detected and restored on every platform, never silently destroyed, and a target that appears after displacement is never overwritten. The quarantine (potentially the only remaining copy of the original) is kept until the new content is verified and the checkpoint lifecycle is durably finalized; rollback conflicts and failures report an explicit uncertain state naming the recoverable quarantine, and the only valid copy is never unlinked before replacement is committed. Undo uses the same quarantine discipline in both directions (undo-delete and undo-create included), so a later user change is never overwritten by a rollback.

## Git inspection and recovery checkpoints

> **Status note (fail-closed).** Git inspection is **unavailable at this stage**: the adapter requires verified Solaris-owned private run directories for every sandboxed Git process, and private run-directory creation and cleanup fail closed because Node offers no directory-relative (openat/mkdirat-style) or delete-by-handle primitive (a same-user process could substitute a verified parent between identity verification and a pathname-based create, and cleanup could delete a substituted object). Nothing Git-related executes. The design below documents the mechanically sound shape that becomes available when an identity-bound run-directory primitive exists: read-only, narrowly executed, and always inside the sandbox — only fixed inspection commands (`git --version`, `git rev-parse`, `git status`, `git diff`) through a dedicated adapter that uses no shell, fixed argument arrays, and an allowlisted subcommand set, executed through the `SandboxBackend` under `validation-offline` with network denied, writes limited to the exact private run directory (the repository is never writable), host reads limited to the repository root and the trusted Git runtime roots, and a confined process tree — so repository-, worktree-, attribute-, environment-, or configuration-controlled helper code (for example clean filters, fsmonitor, diff drivers, pagers, credential helpers) can never run on the host, and any helper Git executes runs inside the same confinement. When the backend cannot enforce the boundary (host-read allowlist, read-only workspace, network denial, process-tree confinement), the adapter reports Git inspection unavailable and Git is never spawned; the adapter itself never spawns a process (enforced structurally by the architecture check).

Command-line overrides are **defense in depth**, not the boundary: the mechanisms that can be enumerated are disabled mechanically (`core.fsmonitor` and the builtin fsmonitor switch, shell aliases — each allowed subcommand is mapped to itself — pagers (`--no-pager` plus pinned `GIT_PAGER`/`PAGER`), external diff programs (`--no-ext-diff`, `diff.external=`), text conversion (`--no-textconv`), credential helpers and prompts (`credential.helper=`, `core.askPass=`, `GIT_TERMINAL_PROMPT=0`), and optional index locks (`GIT_OPTIONAL_LOCKS=0`)). Repository-selected helpers that cannot be enumerated or disabled from the command line — notably `filter.<name>.clean`/`smudge`/`process` filters selected through `.gitattributes` — are NOT claimed to be disabled: their only containment is the enforcing sandbox, and on any host where that sandbox cannot be proven Git is unavailable and never spawned. The live confinement test (`packages/adapters/src/git/cli/git-helper-confinement.test.ts`) proves helper containment **only when it actually runs against a real enforcing sandbox and observes the denial**: a hostile clean filter records distinct bounded outcomes (`filter-ran`, `repo-write-denied`, `network-denied`, `network-connected`, `network-timeout`) into a sandbox-private result channel (its Solaris-controlled HOME inside the private run directory, the only location the profile permits it to write); the test fails unless the filter executed, its repository write probe was denied, its network attempt was denied immediately, and the repository bytes are unchanged. A skipped or unavailable sandbox is reported as skipped, never as passed, and absence of a marker is never treated as proof of denial. The environment is sanitized at the process boundary: repository-redirecting and config-injecting variables (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_*`/`GIT_CONFIG_VALUE_*`, `GIT_CONFIG_PARAMETERS`, askpass/ssh helpers) are stripped even if a caller passes them, and `GIT_CONFIG_NOSYSTEM=1` prevents machine-wide configuration from being read. The resolved executable is re-verified (canonical identity, regular non-link file) immediately before every launch request; byte-for-byte binding to the spawned image is impossible without an exec-by-handle primitive and is not claimed — whatever bytes launch remain inside the enforcing boundary. Output is bounded on raw byte counts with a streaming UTF-8 decoder (truncation never splits multibyte sequences), timeouts and cancellation apply, and structured diff summaries come from NUL-delimited machine-readable numstat data (exact paths including spaces, tabs, unicode, newlines, backslashes, and quotes) rather than human-oriented quoted diff headers. Providers may only select schema-validated high-level options (diff scope, workspace-relative paths) — never raw Git arguments. There is no Git write capability: staging, commits, reset, restore, checkout, clean, stash, branches, worktrees, and remotes are absent, and the architecture check rejects Git mutation command strings and spawn argument lists in runtime code. Repository roots must equal the workspace root; a parent repository never broadens the workspace. Truncated output is reported through explicit truncation flags, not a separate error code.

Every approved workspace mutation first records a durable Solaris-owned checkpoint: versioned metadata plus the exact pre-change bytes, stored outside the workspace at `~/.solaris/checkpoints/<workspace-fingerprint>/<checkpoint-id>/` (fingerprint = SHA-256 of the canonical workspace path). Checkpoints never depend on Git, the Git index, or the working tree; non-Git workspaces get identical protection. No new checkpoint is ever created at this stage — every mutation fails closed as `unavailable` before recording — and `/checkpoints` may still list historical checkpoint data from earlier sessions if any exists; the filesystem checkpoint store and its startup reconciliation are tested internal code, while the former mutation preview/approval/conflict/application logic is deleted and the identity-bound commit design below is documented but not offered until a mechanically identity-bound commit primitive exists.

- **Checkpoints contain local source-code copies.** Preimages may be source code or configuration text. They stay on the local machine: they are never sent to providers, never returned to providers (the store's `loadPreimage` is internal to the undo service), never listed by `/checkpoints`, never indexed by `workspace.search`, and never included in workspace listings. Metadata is bounded and validated on load; preimages are hash-verified against their metadata on read.
- **Storage is fail-closed and tamper-resistant.** Checkpoint metadata is written atomically with private permissions where supported (Windows mode bits alone are not equivalent to POSIX ACL enforcement); every path under the checkpoint root is validated with no-follow semantics on every operation — each component is lstat-checked for symlinks, the leaf must resolve canonically to its logical location (rejecting junctions and reparse points on Windows and links inserted after startup), and the root itself must remain a non-link directory outside the workspace; metadata whose fingerprint or relative path does not match the active workspace is rejected; sizes are bounded; preimage and metadata paths cannot be redirected to shared or attacker-selected paths. Retention is bounded (100 checkpoints / 100 MiB per workspace) and **automatic pruning is disabled**: reaching the count or byte limit fails closed with a typed storage-limit refusal before any write, and no checkpoint or filesystem entry is ever deleted by the store — existing checkpoints are preserved for manual inspection, and `/checkpoints` keeps listing them.
- **A mutation never runs without its checkpoint.** If checkpoint recording fails, the workspace is not modified. If finalization fails after a successful apply, Solaris reports an uncertain recovery state instead of success, and startup reconciliation resolves it from the recorded before/after hashes.
- **Undo is strictly hash-gated.** `/undo` (and `/undo <checkpoint-id>`) requires the current file to match the checkpoint's recorded post-state exactly, revalidated after approval and immediately before the destructive commit; any later user or external change is a `conflict` and nothing is overwritten. Undo shows a complete reverse diff, requires one-time approval, uses the mutation lock and all mutation safety checks, verifies restored bytes against the preimage hash, and marks the checkpoint `undone` only after verification — even if cancellation arrives after the destructive commit point, the lifecycle state is finalized. Startup reconciliation resolves the undo commit ambiguity (a crash between restore and the state update is classified as undone). There is no force undo, no redo, and no provider-accessible undo; providers can never list checkpoint preimages. **Undo fails closed as `unavailable` at this stage**: restoring a checkpoint requires pathname-based displacement and replacement, and Node offers no directory-relative (openat/renameat) primitive, so `/undo` reports `unavailable` before any write, approval, or restore — the discipline above is the tested internal design, not a shipped capability.

## Conformance testing

`npm run test:sandbox` runs fixed internal conformance probes against the real backend: inside-workspace reads and writes, outside-workspace write denial, denied-secret reads, denied host reads (existing regular files in representative unapproved locations outside the approved allowlist — selected independently of the deny surface), cross-run private-directory isolation, loopback, reserved private-network, and DNS network denial, Unix-socket denial, provider-secret absence, descendant-process confinement, output limits, timeout, and cancellation — plus validation-command probes under `validation-offline`: Node scripts (and direct npm CLI invocations as sandbox probes) read fixtures but cannot write the workspace (root, child, grandchild, and npm script shell all denied), cannot reach outbound or loopback network, receive no provider credentials and no `NODE_OPTIONS`, npm pre/post hooks do not run, stdin is closed, output limits terminate the process, timeout and cancellation terminate descendants that ignore normal termination, no sandbox files appear in the workspace, and sandbox-private run-directory cleanup succeeds. The probe sequence also exercises profile isolation in both directions: a broader profile's writes succeed, strict `validation-offline` executions that follow are still denied workspace writes, and a later broader request regains its own (never the strict one's) configuration. The probes use temporary directories and fake secrets only. The command makes no public internet request, never elevates, and returns nonzero when an available backend violates a required boundary. Unavailable backends and backends that cannot enforce the host-read allowlist (Windows) produce a loud skipped result, never a passing one, and probes that cannot execute (for example Unix sockets on an unsupported host) are reported as skipped, never as passed. At this stage private run-directory creation and cleanup fail closed, so the suite cannot construct verified per-run directories and every probe reports skipped loudly with that reason — skipped is never treated as passed.

## Host-read boundary

Sandboxed processes have an enforced deny-by-default host-read allowlist. The runtime's read model allows everything by default, so Solaris denies the entire host root (`/`) and re-allows only the approved surface: the current command's private run directory (with its per-run home/temp/cache), the active workspace when the exact profile allows it, the exact trusted runner executables (and their installation directories), the minimum system runtime/library paths the selected trusted runner requires, and — for requests that carry an explicit read-roots list — exactly those identity-bound paths (never an installation parent containing unrelated data). Everything else — other user profiles, shared temporary areas, other runs (previous or concurrent), mounted volumes, other drives, system configuration beyond the listed runtime paths, service data, logs, caches, and credential locations — is unreadable. No shared Solaris sandbox home/temp is ever granted to a command. Network, loopback, private-network destinations, and Unix sockets are denied for offline execution.

This is an allowlist, not a blocklist of selected directories. On **Linux and macOS** the pinned Sandbox Runtime (`0.0.70`) can express it (deny-root with re-allow); on **Windows** it cannot express a reliable allowlist (per-execution filesystem grants are unsupported, and ACL stamping cannot override inherited well-known-group read access), so Solaris reports the host-read capability as unavailable on Windows and **refuses `process.run` and Git inspection** there instead of claiming a partial boundary (Godot probes are unavailable at this stage on every platform). Live conformance probes verify unreadability of existing files in representative unapproved locations (for example `/etc`, `/opt`, `/usr/local`, `/var`, `/tmp`, `/home`, `/root`, `/mnt`, `/Library`, `/private`, `/Volumes`, `ProgramData`, other profiles, and other volumes) on every platform where the backend runs; an unexpectedly readable existing candidate fails the suite. Unsupported isolation reports unavailable and refuses execution — there is no unrestricted fallback.

## Sandbox wrapper environment contract

The Sandbox Runtime wrapper returns the environment its wrapped invocation requires; Solaris merges exactly that explicit set into its minimal allowlisted child environment. `process.env` is never passed through wholesale: wrapper-only variables are added, collisions with a Solaris-controlled key resolve to the Solaris-controlled value (the wrapper can never override or introduce an alternative spelling of `HOME`, `USERPROFILE`, `TEMP`, `TMP`, or `TMPDIR` — a protected key absent from the base fails closed), wrapper variables matching the credential/proxy/Node-injection deny patterns fail closed, and Windows keys are normalized case-insensitively so `Path`/`PATH` duplicates cannot bypass filtering. On Windows the child environment carries both `HOME` and `USERPROFILE` with the Solaris-controlled sandbox-home value, so a wrapper-provided host profile path can never reach the child.

## Recursive search bounds

`workspace.search` enforces independent global budgets over the entire traversal: directories visited, directory entries examined, regular files considered, eligible files scanned, total input bytes inspected, total output bytes, and elapsed time. Empty directories, oversized files, and non-regular entries consume traversal budget; directories are enumerated incrementally, cancellation is checked during enumeration and scanning, results stay deterministically ordered, and every truncation reports its exact reason.

## Terminal output sanitization

All terminal output — provider responses, repository filenames, Git output, checkpoint metadata, tool activity, errors, and approval information — is untrusted and passes through one final rendering boundary. The sanitizer neutralizes C0/C1 controls, ANSI CSI sequences, OSC sequences (links, title changes, clipboard writes), carriage-return and backspace rewriting, and DEL while preserving ordinary Unicode and newlines; escape sequences split across stream chunks stay inert, and dangling sequences are dropped so truncation can never leave the terminal inside an active escape sequence.

## Sandboxed development-command execution

`process.run` runs a predefined Solaris runner with structured fields — never a provider-supplied shell string, executable path, environment, network permission, writable path, or stdin. **No command can execute at this stage: both runners — `node-script` (one `.js`/`.mjs`/`.cjs` file through the exact `process.execPath`; no provider-controlled Node flags) and `npm-script` — fail closed as unavailable.** `isAvailable()` returns false for both runners, `/commands` shows both as unavailable, and every request is refused during preparation, before any approval; `process.execute` remains `ask` under `develop-offline`, but with every runner unavailable nothing can execute. The pinned Node runtime cannot mechanically bind execution to the approved script bytes: the script can reach internal surfaces such as `process.binding` (e.g. `spawn_sync`) to spawn an unconstrained interpreter, and the staged private copy can be substituted by a same-user process in the verify-to-launch window. Additionally, `npm run` executes whatever script body is present in the workspace `package.json` at npm's own read time — after Solaris's final revalidation — and the pinned Sandbox Runtime cannot bind that read to the approved package bytes without copying the broader package state (content-override binds are Linux-only internals that degrade to read-denial on macOS and are unsupported on Windows, and private-directory execution breaks the cwd-relative behavior of normal repository scripts). A changed post-approval script could otherwise execute, so every command request is refused with that reason instead of claiming exact approval.

- Every command requires explicit one-time approval of the exact immutable plan. The approval shows the full execution boundaries (read-only workspace, denied network, minimal environment, closed stdin, timeout, output limits), the immutable-execution notice, and the digest prefix. The digest is a SHA-256 over the runner, trusted executable identity and version, script path and complete script SHA-256, arguments, working directory, effective profile, environment policy, timeout, output limits, stdin policy, and network policy.
- The approved plan may execute exactly once. Immediately before execution every precondition is revalidated (working directory, script file and hash, trusted executable identity, capability policy, sandbox availability, and the recomputed digest); any change is a `conflict` and nothing runs under an earlier approval.
- **The executed bytes are the approved bytes, and the executable boundary is exactly one self-contained file — the `node-script` design, not offered at this stage.** The design: after revalidation the script's exact bytes are copied into the current run's private directory with exclusive creation, the private copy's hash is verified against the approved hash, and the child would execute the immutable private copy — never the mutable workspace path. `node-script` is a deliberately dependency-free runner: the approved single file must be self-contained, and every code-loading mechanism is denied mechanically at runtime, not by source inspection — `import`/`import()`/ESM resolution (a process-wide resolve hook that rejects every specifier), `require`/`Module._load` (patched to throw), worker-thread code files (`Worker` shadowed), `eval`/`new Function` (`--disallow-code-generation-from-strings`), and native addons (`--no-addons`). A script that attempts to load additional code fails closed; no unapproved module ever executes. The approval digest binds the single entry file's SHA-256, and the approval notice states this boundary exactly: the script runs alone from the immutable private copy, `__dirname`/`import.meta.url` refer to that copy, `process.cwd()` stays in the workspace, and imports do not resolve through the workspace. The staged copy and bootstraps are re-verified immediately before the execution request would be returned; the residual window between that verification and the backend's spawn would lie inside the Solaris-private (0700) run directory and is documented, not claimed closed. None of this executes at this stage: the pinned Node runtime cannot bind execution to the approved script bytes — the script can reach internal surfaces such as `process.binding` (e.g. `spawn_sync`) to spawn an unconstrained interpreter, and the staged private copy can be substituted by a same-user process in the verify-to-launch window — so `node-script` fails closed as `unavailable`, exactly like `npm-script`.
- Commands execute only through the `SandboxBackend` under `validation-offline`; the backend must report full host-read allowlist, read-only workspace, network-denial, and process-tree confinement capability or the command does not run (fail closed). There is no host-process fallback.
- **Private run directories are unavailable at this stage.** The design — each run gets a verified Solaris-owned directory beneath `~/.solaris/runs/<workspace-fingerprint>/<run-id>/` with private `home/`, `tmp/`, `npm-cache/`, and a script cache; the runs root and every path component verified with no-follow semantics before anything is created beneath them; exclusive creation with the verified parent identity re-checked immediately before each create; the full chain re-verified canonically before use; the runs root outside the workspace; the sandboxed command granted exactly its current run directory — is NOT offered, because Node offers no directory-relative (openat/mkdirat-style) or delete-by-handle primitive: a same-user process could substitute a verified parent between identity verification and the pathname-based create, and cleanup could delete a substituted object. The provider performs zero filesystem operations: creation reports `unavailable` before creating anything, and cleanup reports a truthful failure while preserving anything that exists. The design becomes available when a mechanically identity-bound create/delete primitive exists.
- Output streams to the CLI as bounded decoded UTF-8 events (16 KiB per event, line-oriented rendering, terminal sequences sanitized on display). Hard limits are 1 MiB per stream, accounted on raw bytes and enforced within the crossing chunk; exceeding them terminates the process (`output-limit`). Truncation never splits a multibyte sequence. The provider receives at most 256 KiB per stream with explicit truncation markers and an omitted-bytes note. Nonzero exits are normal completed commands (`exitCode: 2`), never infrastructure failures.
- Timeouts (default 120 s, provider-bounded to 10 minutes) and cancellation terminate the complete process tree, including descendants that ignore normal termination. Cancellation removes timers and listeners, releases the execution lock, attempts run-directory cleanup, and returns the prompt.
- Commands are serialized with the same in-process lock as approved file mutations: a mutation cannot begin while a command runs and vice versa.
- Git structured status is recorded before and after execution as a verification signal. A detected workspace change marks the result `workspace_violation`, disables further command execution for the session, and instructs the user to inspect the workspace; Solaris never auto-repairs. The OS sandbox remains the security boundary; Git status is a signal, not the boundary.
- Bounded in-memory session metadata is kept for completed commands (command id, runner, safe summary, digest, start time, duration, exit code, outcome, truncation flags); full output is never persisted, and `/commands` shows the latest five records.

## Godot probe security model

> **Status note (fail-closed).** Engine probing is **intentionally unavailable at this stage**: the probe runner reports `unavailable` for every probe and never spawns the executable, because the backend re-opens the staged copy's pathname at spawn time and a same-user process can substitute bytes between final verification and launch (no exec-by-handle primitive). No engine profile can be produced, `godot.inspect_engine` cannot return a profile, `/godot-installations` lists unprofiled candidates with the reason, and `--godot-doctor` exits nonzero (no valid engine). The engine-profile cache is an **explicitly unavailable no-op component**: it is never initialized, created, read, or written (`load()` is always a miss, `store()` returns a typed unavailable result, `count()` is 0, and the doctor reports it disabled), because Node offers no directory-relative or handle-relative primitive with which a cache write could be bound to a verified parent object — the earlier storage implementation was removed rather than retained as an unsafe surface. The profile and rules below document the design for a future mechanically identity-bound launch primitive; probes fail closed rather than running under a weaker model. Solaris does not open, import, execute, or run a Godot project at this stage (recovery-mode project probing is not implemented).

Godot engine probing reuses the existing sandbox boundary through the internal `godot-probe-offline` profile:

- **Fixed arguments only.** The probe adapter constructs every probe argument tuple through one narrow `fixedProbeArguments` constructor private to the adapter: exactly `--version`, `--help`, and `--dump-extension-api` — never `--path`/`--upwards`/`--import`/`--scene`/`--script`/`--editor`. There is no project path, no project working directory, and no provider-supplied argument; the provider can never select an executable or pass arguments. The architecture check mirrors this boundary structurally plus regex/text checks: non-fixed `--` tokens, concatenated construction, imported argument arrays, and construction outside the fixed runner are rejected in probe invocation code (a developer guardrail, not an OS security boundary; the runtime boundary is the private constructor).
- **Executable identity binding.** Every probe recomputes the complete bounded SHA-256 of the canonical executable path and re-verifies a regular non-link file and unchanged canonical identity before running; size+mtime are never treated as identity. Execution binds to the verified bytes: the probe stages a private executable copy inside its run directory (exclusive creation, size-bounded, verified copy hash, executable mode), and only the verified private copy is executed — never the mutable configured path — so a same-size replacement with a restored mtime, a replacement between hash and spawn, or a symlink/junction target substitution can never execute under an old fingerprint. Cache hits revalidate the same full SHA-256 before a cached profile is served.
- **Project independence.** Probes run without a project and are identical for every workspace; nothing project-derived influences the probe command. Project files are untrusted data and can never select an executable. The workspace path appears nowhere in probe requests — not in the executable, arguments, working directory, environment, or sandbox configuration — and the `godot-probe-offline` profile excludes the workspace from readable roots; the request's explicit read-roots list grants only the exact required identity (the private copy inside the run directory), never an installation parent containing unrelated data.
- **Sandbox gating requires the host-read boundary.** Probes run only when the backend reports available with every restriction — host-read, write, network, and process-tree — and fail closed otherwise; on Windows the backend never reports generally available (setup and host-read capability are separate conditions: setup can be complete while host-read enforcement is unavailable), so probes are refused there.
- **Private probe directories.** Probes run from a Solaris-private run directory under `~/.solaris/runs` with per-run home/temp. The API dump lands in the run temp and is deleted after parsing; `--dump-extension-api` counts as verified success only when the sandbox result is completed, the exit code is exactly zero, the expected dump exists as a regular non-link file within the size bound, parsing succeeds, the fingerprint is over the exact raw dump bytes, and cleanup is recorded truthfully — a nonzero exit with a valid-looking dump is never success. Exactly `extension_api.json` is expected; unexpected files are ignored and never trusted. Cancellation kills the Godot process tree, removes run directories and partial dumps, and caches nothing.
- **Network denied.** The `godot-probe-offline` profile denies outbound network; probes cannot reach the internet.
- **Credential absence.** Probe environments carry no provider or project credentials; the child environment comes from the same allowlisted builder as command execution.
- **Workspace containment.** Probe working directories are Solaris-owned run directories, never the workspace; the workspace is neither writable nor readable during probing (excluded from the profile's readable roots), and executables inside the project workspace are rejected by default.
- **Fail closed.** If the sandbox backend is unavailable or cannot enforce the profile, the probe does not run — no host-process fallback, no weakened profile, no unrestricted backend.
- **Untrusted project files.** `project.godot`, plugin descriptors, and scanned sources are parsed statically, bounded, and never evaluated or executed; they can never influence probe invocation.
- **Provider-visible safe subset.** Provider-visible results use installation ids and executable fingerprints. Absolute paths, raw help output, and complete API dumps never enter provider context; only bounded normalized metadata is kept, and the complete dump is never persisted.
- **Cache privacy (design note).** The intended engine-profile cache at `~/.solaris/godot/engine-profiles` would store only bounded normalized data — never credentials, complete dumps, project files, or absolute project paths — keyed by executable SHA-256 and validated by recomputing the executable's full SHA-256 before a hit is served (never size+mtime). At this stage the cache is an explicitly unavailable no-op (see the status note): nothing is stored, read, created, or removed, and the doctor reports it disabled. Discovery re-collects candidates and re-validates identities on every call, so candidate additions, removals, and content changes are visible within a session.
- **No approval for fixed probes.** `godot.inspect` is `allow` in every built-in policy and requires no one-time approval because probes are fixed, project-independent, read-only, and offline; explicit executable paths are user configuration, not provider input.
- **The CLI never runs Godot.** Only the Godot probe adapter would invoke the engine, always through the sandbox backend; at this stage probing fails closed, so nothing spawns Godot. Providers never run Godot.

## Why arbitrary command execution remains deferred

No general shell, arbitrary executable runner, writable command execution, package installation (`npm install`/`ci`/`update`/`exec`/`npx`), interactive stdin, background process, or remote execution exists. The sandbox, profiles, policy evaluator, environment filtering, and conformance suite exist so those tools — when a binding mechanism exists — execute under enforcement from the first day. Both runners (`node-script` and `npm-script`) are defined but fail closed as unavailable: the pinned Node runtime cannot mechanically bind execution to the approved script bytes — the script can reach internal surfaces such as `process.binding` (e.g. `spawn_sync`) to spawn an unconstrained interpreter, and the staged private copy can be substituted by a same-user process in the verify-to-launch window — so no validation command can execute at this stage.

## Why full-access mode does not exist yet

No legitimate current use case justifies an unrestricted profile. It would defeat the security boundary this document describes, and it is deliberately not implemented.
