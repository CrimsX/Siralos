# Roadmap

Six agreed product stages. Each stage is a milestone, not a feature catalogue.

## 1. Harness foundation

An executable, provider-neutral foundation: interactive CLI, provider port, deterministic fake provider, in-process sessions, engineering standards, mechanically enforced architecture, a secure bounded tool loop with read-only workspace inspection tools, a sandbox/permission boundary (capability policy, built-in profiles, an isolated Sandbox Runtime backend with an enforced host-read allowlist, allowlist child environments, fixed conformance probes), the workspace-mutation machinery (intended design, unavailable today: create, exact-replacement edit, delete — each with complete previews, one-time approval, hash conflict detection, identity-bound quarantine commits, and post-write verification), read-only Git inspection plus Solaris-owned recovery checkpoints and conflict-safe undo (trusted Git execution, `git.status`/`git.diff`, durable per-file checkpoints, fail-closed retention — no automatic pruning (the byte limit counts actual stored regular-file bytes beneath the checkpoint directory including metadata and preimages; declared preimage bytes are hash-verified through a handle-bound bounded read loop with a pre-read/final stability snapshot during capacity checks (same-content substitutions and same-inode in-place rewrites are refused), preimage limits are capped with larger configurations rejected at store creation, operations are bound to their before/after existence states, and unexpected checkpoint content makes capacity unverifiable and is never repaired or deleted), crash reconciliation, `/git-status`, `/diff`, `/checkpoints`, `/undo`), and the sandboxed validation-command surface (`process.run`, structured arguments only, read-only workspace, denied network, minimal environment, closed stdin, bounded streamed output, digest-bound one-time approval, timeouts, process-tree cancellation, `validation-offline` profile, command conformance probes, `/commands` and `/cancel`). **Stage 1 is NOT complete: several foundation capabilities are intentionally unavailable.** The mutation tools and `/undo` fail closed as `unavailable` before any write, approval, or checkpoint, because Node offers no directory-relative (openat/renameat) primitive and a same-user process can swap a parent or target at any instruction boundary — the mutation entry points are unavailable stubs; the core contracts, reusable primitives (path validation, diffing, hashing, the mutation lock, safe-replacement helpers), and the filesystem checkpoint store remain as tested internal code, while the former preview/approval/application logic was largely deleted and the identity-bound commit design is documented as future work; no approval for mutations is ever requested, and no new checkpoint is ever created at this stage (historical checkpoint data from earlier sessions, if any, may still be listed), and automatic checkpoint-retention pruning is disabled — storage pressure fails closed with a typed storage-limit refusal and deletes nothing, and any checkpoint whose capacity contribution cannot be verified (unreadable or invalid metadata, missing/oversized/linked preimages, size disagreement) blocks new checkpoint creation; existing checkpoints are preserved for manual inspection. Both runners — `node-script` and `npm-script` — are defined but fail closed as unavailable: the pinned Node runtime cannot mechanically bind execution to the approved script bytes (the script can reach internal surfaces such as `process.binding` (e.g. `spawn_sync`) to spawn an unconstrained interpreter, and the staged private copy can be substituted by a same-user process in the verify-to-launch window), so no validation command can execute at this stage, and private run-directory creation is unavailable for the same reason. Git inspection is unavailable at this stage: the adapter requires Solaris-owned private run directories, whose creation and cleanup fail closed (no directory-relative or delete-by-handle primitive in Node); Git can only ever execute inside an enforcing sandbox backend and is never spawned outside it. The validation suite (`npm run check`) runs on this machine, but the capabilities above are intentionally unavailable — they are surfaces (and, where retained, tested internal machinery), not shipped capabilities.

## 2. Godot script-development MVP

Godot project detection and understanding, GDScript-first programming workflows, and file-scoped edits validated against the project.

**Milestone: Godot executable discovery and static project profiling (incomplete — engine probing is intentionally unavailable).** Engine discovery happens before any project execution: trusted user-configured installations (absolute paths only, optional edition hints) plus fixed-name PATH search — no broad filesystem scanning, no registry/Spotlight/package-database searches, no shell. Every candidate is fingerprinted exactly (canonical path, size, mtime, SHA-256) with full-hash revalidation. **Engine probing fails closed as unavailable at this stage**: the probe runner reports `unavailable` and never spawns the executable, because the backend re-opens the staged copy's pathname at spawn time and a same-user process can substitute bytes between final verification and launch (no exec-by-handle primitive). No engine profile can be produced, `godot.inspect_engine` cannot return a profile, and the engine-profile cache is an explicitly unavailable no-op component (never initialized, created, read, or written: `load()` is always a miss, `store()` returns a typed unavailable result, `count()` is 0, and `--godot-doctor` reports it disabled); `/godot-installations` lists unprofiled candidates with the reason, and `--godot-doctor` exits nonzero (no valid engine). The designed probe path — project-independent fixed probes (`--version`, `--help`, `--dump-extension-api`, fixed tuples built by a single private constructor) through the sandbox backend under the internal `godot-probe-offline` profile (workspace excluded from readable roots, host-read boundary required, execution bound to a verified private executable copy), adversarial version parsing that preserves release channels, conservative edition classification, deterministic selection ranking with recorded rationale (explicit selections never fall back silently) — is documented but not offered at this stage. Static project detection reads only the root `project.godot` (never parents/children, nothing evaluated), and the executable-content inventory covers tool scripts, editor plugins, GDExtension descriptors, autoloads, and C# project files without loading or running anything — every project-controlled path is lexically and canonically contained, the traversal is globally bounded, and every inspection rescans the complete project (no profile cache). The surface: `godot.inspect_engine` / `godot.inspect_project` provider tools, `/godot`, `/godot-installations`, `/godot-project`, `/godot-doctor`, the `--godot-path` / `--godot-installation` / `--godot-doctor` startup flags, `SOLARIS_GODOT` / `SOLARIS_GODOT_INSTALLATION` overrides, and the opt-in live conformance (`SOLARIS_TEST_GODOT="<absolute-path>" npm run test:godot`, which reports UNAVAILABLE loudly at this stage, never passes, and never modifies the user-supplied engine).

The intended sequence for stage 2: Godot executable and project discovery → version-matched Godot knowledge profile → GDScript project intelligence → read-only import and parse diagnostics → Godot script-development MVP. **The first milestone (discovery and static project profiling) is not complete while engine probing is unavailable.** The recovery-mode project-probing surface (ADR 0009) is restored ahead of that sequence as contracts, bounded static preparation, a one-time approval protocol with expiring single-use prepared probes, diagnostics, CLI reporting, and structural architecture enforcement — with **execution fail-closed unavailable on every platform** (the disposable mirror and the recovery runner never create, delete, or launch anything, because Node offers no exec-by-handle, directory-relative create, or delete-by-handle primitive); it becomes operational only after an identity-bound execution primitive exists.

**Milestone: version-matched Godot knowledge profiles and GDScript check-only diagnostics (ADR 0010) — contracts and fail-closed surfaces implemented; generation and check-only execution intentionally unavailable.** The exact-engine API knowledge layer (profile model bound to the executable SHA-256, API dump SHA-256, and knowledge schema; the `--dump-extension-api-with-docs` dump parser; the bounded deterministic index over classes, methods, properties, signals, constants, enums, utility functions, built-in classes, and operators; literal/token search and exact lookup with deterministic ranking; manual-documentation-channel classification) and the authoritative read-only GDScript diagnostic layer (workspace-relative script validation and hashing, bounded deterministic enumeration, conservative engine-output normalization with engine-version fixtures, deterministic aggregation, the fixed `--headless --path <disposable-mirror> --script <mirror-script> --check-only` invocation, one-time approval bound to script hashes, risk-manifest digest, command digest, sandbox profile, and limits) are implemented as tested contracts, adapters, provider tools (`godot.api_search`, `godot.api_lookup`, `godot.check_script`, `godot.check_project_scripts`), CLI commands (`/godot-knowledge`, `/godot-api`, `/godot-knowledge-refresh`, `/gdscript-check`, `/gdscript-diagnostics`), architecture enforcement, and the opt-in `npm run test:godot-diagnostics` conformance. **Generation and check-only execution fail closed as unavailable on every platform**: the fixed runners never spawn the executable and the knowledge cache is an explicitly unavailable no-op (never initialized, created, read, or written), because Node offers no exec-by-handle, directory-relative create, or delete-by-handle primitive; no approval is requested while execution is unavailable, nothing is created, and no engine is launched. **Milestone: bounded Godot GDScript LSP client (ADR 0011) — contracts and fail-closed surfaces implemented; session startup intentionally unavailable.** The language-session layer (provider-neutral session port, incremental LSP framing, bounded JSON-RPC client with correlation/timeouts/cancellation/server-request rejection, file-URI mapping, conservative diagnostics/hover/completion/definition normalization, loopback-only dynamic port allocation, the fixed `--headless --editor --recovery-mode --path <mirror> --lsp-port <allocated>` runner, one-time session approval bound to the risk manifest/executable/mirror policy/capability set/sandbox/LSP policy, staleness revalidation, provider tools, CLI commands, `/status` reporting, architecture enforcement, and the opt-in `npm run test:godot-lsp` conformance) is implemented as tested contracts and adapters. **Session startup fails closed as unavailable on every platform**: the LSP runner never spawns the editor, no mirror is created, no port is opened, no approval is requested while execution is unavailable, and the live isolation probe is reported skipped, never passed. The next narrow task after this milestone is the LSP-assisted GDScript edit/repair loop: inspect → propose edit → approve → checkpoint → apply → recreate/update the disposable language session → diagnose → repair.

**Milestone: GDScript development quality gates and independent review (ADR 0013) — the Stage 2 completion gate, contracts and fail-closed surfaces implemented; the quality stage intentionally unavailable while the change-set applier is fail-closed.** The quality layer separates deterministic quality gates (approved change applied, checkpoint recorded, scope verified, parser, LSP errors, required validation, independent review — hard; warnings, conventions — soft; diff metrics — informational) from one dedicated read-only model-based reviewer with a fresh provider context and a composition-root-owned read-only tool registry. Warning policy respects Godot/project behavior with conservative baseline/delta attribution; conventions follow repository/local/project guidance with Godot style as fallback and never force static typing; validation planning discovers only existing `check`/`test`/`lint`/`typecheck` scripts and runs each through the existing one-time process-approval flow (denial/unavailability is `validation_incomplete`, never `passed`); blocking Critical/High findings are repaired through separately approved, fully revalidated change sets with fresh holistic re-review (at most 2 review-repair rounds); `/quality` and `/review-change` render the report and run a fresh read-only review; `/develop` automatically enters the quality stage before completion. The quality stage, reviewer plumbing, and validation executor are tested internal code exercised through injected fakes, **but the stage cannot run in the shipped product while the change-set applier fails closed** (no directory-relative commit primitive in Node): no quality stage, review, or validation command executes, no approval is requested, and nothing is created or deleted; the opt-in `npm run test:godot-quality` conformance verifies this truthfully and always reports the live quality-stage isolation probe as skipped, never passed.

## 3. Godot-native development MVP

Godot editor and runtime integration: scene/resource manipulation, editor-aware workflows, and engine-validated changes.

## 4. Runtime and visual QA

Automated testing, debugging, visual gameplay verification, and performance profiling against a running Godot project.

## 5. Extensibility and optional agents

Skills, game-development-specific agent profiles, and optional user-invoked multi-agent review and comparison.

## 6. Controlled evolution and stable release

Controlled `/evolve` self-improvement workflows, hardening, and a stable release.

Stages 3–6 are not started. Stage 1 (harness foundation) is not complete: workspace mutations, `/undo`, and command execution are intentionally unavailable, and Git inspection is unavailable at this stage (the adapter requires Solaris-owned private run directories, whose creation and cleanup fail closed). Stage 2 is the current stage; its first milestone (Godot executable discovery and static project profiling) is not complete while engine probing is unavailable, the version-matched Godot knowledge and GDScript check-only diagnostic surfaces (ADR 0010), the bounded GDScript LSP surface (ADR 0011), the GDScript development workflow (ADR 0012 — the complete edit/validate/repair loop with exact change sets, one-time approvals, mandatory checkpoints, `--check-only` and fresh-LSP validation gates, validation evidence, and bounded repairs), and the quality gates and independent review (ADR 0013 — deterministic hard/soft gates, warning baselines, convention analysis, validation planning through one-time process approval, the fresh-context read-only reviewer, bounded review-repair rounds, `/quality` and `/review-change`) are implemented as contracts, change-set machinery, orchestration, CLI commands, deterministic fixtures, and truthful reporting — with generation, check-only execution, session startup, the change-set applier, and the quality stage failing closed as unavailable on every platform (nothing executes, no approval for a mutation is ever requested, no checkpoint is ever created, and no review or validation command runs until identity-bound primitives exist).
