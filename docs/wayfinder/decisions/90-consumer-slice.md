# 90 — The Consumer Slice

Governing plan 68 · entry review [79](79-context-management-foundations.md) · Map.

> **User-directed 2026-08-31 (session HITL).** The consumer slice closes the loop: HOT assembles L1 summaries by default with deeper levels reachable only through the read-only expand tool and the demand edge (the decision 88 curve finding makes rank-only auto-escalation unadoptable — the runtime does not guess depth), hot nodes carry a bounded 1-hop neighbor map of ids+digests, and the end-to-end demand composition exists as tested pure composition with live activation still precondition-gated per decision 84.

## 2. Amendments

| Amendment                        | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| B1 L1-default assembly           | HOT tier contributes each hot node's L1 SUMMARY to the assembled context by default — the 4096 budget and 1024 pinned-HOT quota count the assembled SUMMARY tokens (unique-digest). Deeper representations are NEVER auto-assembled and NEVER auto-escalated by the scheduler; deeper content is reachable ONLY through the read-only `context.expand` tool, whose demand flows back through the A1 demand edge. Decision 88's finding is the recorded justification: rank-only escalation loses structured depth (13/14 at every k), so the runtime does not guess depth — the model escalates explicitly, and demanded nodes stay hot via the demand edge. |
| B2 Neighbor prefetch             | Each assembled HOT node carries a bounded 1-hop neighbor map: at most 8 neighbors, selected deterministically (neighbors ordered by `node_id` ascending, first 8), each stub carrying ONLY the neighbor's `node_id` and content digest — NEVER content. Stubs are counted in the budget accounting honestly (their bytes estimate via the same `estimate_tokens` estimator, no tool-call overhead), subject to the unique-digest rule where applicable. Prefetch does not pull content and does not change tier membership of neighbors.                                                                                                                     |
| B3 End-to-end demand composition | A pure, tested composition path `tool-round -> events -> tick`: given a tool call + result, `derive_access_events` produces the events (existing helper); the host accumulates them and passes them into the next `TickInput`. Implemented as a pure function at the adapters boundary (`derive_events_for_tick` / `compose_tick_input` over `ToolObservation`, no mutable global state, no CLI live wiring beyond what exists); live activation remains precondition-gated per decision 84 — the composition is proven by tests only. The model can never inject events; they come only from host-observed tool results.                                    |
| Assembly order (pinned)          | Tick pipeline per decision 89 (coalescing, stale demotion, demand updates, recompute, promotion gate, pin quota, budget) -> assembly: hot nodes sorted canonically -> per node: L1 summary contribution + neighbor stubs (B1, B2) -> budget enforcement over the assembled set (unique-digest, pinned quota 1024 then budget 4096, demoting lowest-scored HOT nodes, `node_id` asc tiebreak).                                                                                                                                                                                                                                                                |
| Seam rules                       | The assembly is deterministic synchronous integer scoring, demotion never deletes, tools remain read-only, no embeddings/lexical-only routing (clause d) holds, decision 84 precondition gate (live registration) is NOT flipped. Assembly never pulls deeper levels and never mutates neighbor tiers; stub cost is honest and digest-deduped.                                                                                                                                                                                                                                                                                                               |
| Frozen guard                     | The context-benchmark record (corpus v65, decisions 87 GO / 88 Retained) must remain BYTE-IDENTICAL — the benchmark flow passes no events and its scheduler path must be untouched. If the benchmark output changes, treat it as a scope defect and fix the scheduler change, never the benchmark.                                                                                                                                                                                                                                                                                                                                                           |
