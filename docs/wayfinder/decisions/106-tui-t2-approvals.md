# 106 — TUI T2: The Approval Surface

Ticket [103](../tickets/103-siralos-tui.md) · entry review [103](103-siralos-tui-entry-review.md) · Map.

> **User-directed 2026-08-31 (session HITL).** T2 of the approved TUI arc: approval prompts render as TUI modals — same host-gated evaluation, new presentation; the modal keys route y/n/Esc through the same decision read the stdio path uses; the T1 dispatch-duplication debt consolidation starts where the modal work naturally touches it; while a modal is pending no other keys pass.

## 2. Design (B1–B4 + consolidation ledger) — as implemented

| ID  | Design                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Evidence / note                                                                                                                                                                                                   |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B1  | MODAL MODEL: `TuiState` gains `pending_approval: Option<ApprovalModal { lines: Vec<String> (the sanitized approval request exactly as the stdio path renders it), selected: bool }>` — the modal renders centered over the transcript pane with a dimmed backdrop (`Clear` + bordered block titled `Approval required (y/n, Esc deny)`); keys: `y` approve, `n` deny, `Esc` deny. While a modal is pending, ALL other keys are ignored except the modal keys: `handle_key` returns false without mutating, and the live loop branches to `handle_modal_key` only (no typing through a modal).                                   | `tui.rs` `ApprovalModal`, `pending_approval`, `draw` overlay, `handle_key` gate, `handle_modal_key`; live-loop modal branch in `run_interactive_tui_with_options`; `keys_ignored_while_modal_pending`             |
| B2  | SAME GATES, NEW PRESENTATION: the approval decision routes through the SAME host-gated evaluation the stdio path uses — one definition, `evaluate_approval_input` in `tui.rs` (`y` case-insensitive trimmed approves, anything else denies). The stdio path reads via the input-queue seam (`read_approval_via_input_queue`: `BufRead::read_line` then the same evaluation); the modal's `y`/`n` feeds the same evaluation via `evaluate_approval_char`, `Esc` maps to deny. The approval evaluation code is unchanged and un-reimplemented — no parallel approval logic.                                                       | `tui.rs` `evaluate_approval_input` / `evaluate_approval_char` / `modal_key_decision`; `interactive.rs` `read_approval_via_input_queue`, `shared_evaluate_approval`; `approval_y_routes_approve_through_same_gate` |
| B3  | DEBT CONSOLIDATION (starts): shared now — `evaluate_approval_input`, `evaluate_approval_char`, `modal_key_decision`, `handle_modal_key`, `ApprovalModal::new`, plus the `interactive.rs` shims `read_approval_via_input_queue` / `shared_evaluate_approval` / `build_approval_modal` that both loops call (single definitions, no copies). Still duplicated (T3–T4 owe it) — the session-composition block, the slash-command dispatch match (`handle_tui_line` vs the stdio loop), and the inline key-edit handling in the live loop (which `handle_key` shadows but the loop does not yet call). No forced big-bang refactor. | `consolidated_helper_is_same_function_both_loops_call` (compile-level same-function proof); ledger in §3                                                                                                          |
| B4  | BOUNDS: the modal request lines are bounded — `ApprovalModal::new` keeps at most the last `MAX_APPROVAL_LINES` (30) lines with the `APPROVAL_TRUNCATION_MARKER` (`... (truncated)`) appended on truncation (the stdio render is already bounded). The modal never renders unsanitized content: it stores verbatim only lines already sanitized upstream (same render as stdio), and the live-loop verdict lines are static host strings (`Approved.` / `Denied.`).                                                                                                                                                              | `tui.rs` `MAX_APPROVAL_LINES`, `APPROVAL_TRUNCATION_MARKER`; `modal_line_bound_with_truncation_marker`                                                                                                            |
