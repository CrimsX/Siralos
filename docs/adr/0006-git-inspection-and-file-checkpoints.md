# ADR 0006: Git inspection and file checkpoints

Status: accepted

> **Status note (fail-closed).** The checkpoint and undo machinery in this ADR is **not offered at this stage**: every mutation entry point and `/undo` fails closed as `unavailable` before any write, approval, or checkpoint, because Node offers no directory-relative (openat/renameat) primitive (see ADR 0005). No new checkpoint is ever created at this stage (historical checkpoint data from earlier sessions, if any, may still be listed). **Git inspection is also unavailable at this stage**: the adapter requires verified Siralos-owned private run directories for every sandboxed Git process, and private run-directory creation and cleanup fail closed because Node offers no directory-relative or delete-by-handle primitive. The adapter's boundary design below (Git can only ever execute inside an enforcing sandbox backend and is never spawned outside it) remains the mechanically sound shape that becomes available when an identity-bound run-directory primitive exists.

## Context

Siralos can apply approved workspace mutations but has no repository awareness and no recovery mechanism: a crashed mutation, or a Siralos edit the user later regrets, cannot be undone without manual work. Before Siralos is permitted to execute development commands, it needs read-only Git inspection and a Siralos-owned recovery record. This milestone adds trusted Git status/diff, durable per-file checkpoints around every approved mutation, crash reconciliation, and user-invoked, approval-gated safe undo. Checkpoints are deliberately independent of Git: they must work in non-Git workspaces and must never depend on the Git index, stashes, or commits.

## Decision

- **Git access is read-only in this milestone.** Siralos executes only fixed inspection operations (`git --version`, `git rev-parse`, `git status`, `git diff`). Staging, commits, reset, restore, checkout, clean, stash, branches, worktrees, remotes, hooks, and config edits are absent; the architecture check forbids Git mutation command strings and spawn argument lists in runtime code.
- **Git always runs inside the sandbox backend.** Git processes execute under `validation-offline` with network denied, writes limited to the exact private run directory (the repository is never writable), host reads limited to the repository root and the trusted Git runtime roots, and a confined process tree — so repository-, worktree-, attribute-, environment-, or configuration-controlled helper code (for example clean filters) can never run on the host; any helper Git executes runs inside the same confinement. When the backend cannot enforce the required boundary (host-read allowlist, read-only workspace, network denial, process-tree confinement), the adapter reports Git inspection unavailable and Git is never spawned. The adapter itself never spawns a process; raw Git process primitives are private to the adapter and executed through the backend. The resolved executable is re-verified (canonical identity, regular non-link file) immediately before every launch request; byte-for-byte binding to the spawned image is impossible without an exec-by-handle primitive and is not claimed — whatever bytes launch remain inside the enforcing boundary.
- **Git uses fixed argument arrays, never a shell.** The Git adapter spawns the executable directly with a fixed allowlisted subcommand set, an exact argument array, `--no-pager`, and `--literal-pathspecs`. Provider input can only select schema-validated high-level options (diff scope, workspace-relative paths) — never raw Git arguments.
- **Command-line overrides are defense in depth, not the boundary.** The configuration mechanisms that can be enumerated are disabled mechanically with command-line overrides that repository configuration cannot re-enable: `core.fsmonitor` and `core.useBuiltinFSMonitor`, shell aliases (each allowed subcommand maps to itself), pagers, `diff.external`, text conversion, `core.askPass`, and `credential.helper`/`credential.interactive`. Command-line `-c` settings take precedence over repository, user, and system configuration, and Siralos builds the argument array itself, so later arguments cannot re-enable a disabled behavior. Repository-selected helpers that cannot be enumerated or disabled from the command line — notably `filter.<name>.clean`/`smudge`/`process` filters selected through `.gitattributes` — are NOT disabled mechanically: their only containment is the enforcing sandbox, and on any host where that sandbox cannot be proven Git is unavailable and never spawned.
- **Git output is treated as untrusted.** Pagers, external diff programs, and text-conversion filters are disabled (`GIT_PAGER=cat`, `PAGER=cat`, `--no-ext-diff`, `--no-textconv`, `--no-color` where accepted); credential prompts are impossible (`GIT_TERMINAL_PROMPT=0`); optional index locks are disabled (`GIT_OPTIONAL_LOCKS=0`); `GIT_CONFIG_NOSYSTEM=1` prevents machine-wide configuration from being read; repository-redirecting and config-injecting environment variables (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_COMMON_DIR`, `GIT_NAMESPACE`, `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_*`/`GIT_CONFIG_VALUE_*`, `GIT_CONFIG_PARAMETERS`, `GIT_ASKPASS`, `SSH_ASKPASS`, Git SSH helpers, `GIT_EXTERNAL_DIFF`) are stripped at the process boundary even if a caller passes them; stdout and stderr are independently bounded on raw byte counts with a streaming UTF-8 decoder (truncation never splits multibyte sequences); output is locale-stable (`LC_ALL=C`, `LANG=C`); commands run from the workspace root with a sanitized environment and no network. Errors are normalized into safe categories (`git_unavailable`, `git_not_repository`, `git_root_mismatch`, `git_status_failed`, `git_diff_failed`, `git_cancelled`, `git_timeout`, `git_parse_failed`); bounded output is reported through explicit truncation flags rather than an error code.
- **Status uses a machine-oriented format.** `git status --porcelain=v2 -z --branch --untracked-files=all --ignore-submodules=all` is parsed into a structured model with ordinary, renamed/copied, unmerged, and untracked records; branch, detached, unborn, upstream, and ahead/behind information; tracked type changes classified as modified; adversarial filename support; explicit entry-limit truncation; and workspace-relative `/`-separated paths.
- **Diffs are bounded and summary-first.** `git diff` runs with external helpers disabled and path lists prefixed with `--`; structured file summaries come from NUL-delimited machine-readable numstat data (exact paths including spaces, tabs, unicode, newlines, backslashes, and quotes; rename pairs; binary classification; line counts) rather than human-oriented quoted diff headers; the unified patch is retained only for display. Output is capped (patch bytes, changed files), binary changes are summarized without binary patches, untracked contents are excluded with an explicit note, unborn repositories yield an empty head diff, and truncation is reported.
- **Repository roots cannot broaden the workspace.** The Git adapter canonicalizes the repository root and requires it to equal the Siralos workspace root; a nested launch directory reports `root_mismatch` instead of silently widening scope, and non-Git workspaces remain fully valid (checkpoints and undo never require Git).
- **Checkpoints do not use Git stash or reset.** A checkpoint is a Siralos-owned record: versioned metadata plus the exact pre-change bytes of one file, stored outside the workspace at `~/.siralos/checkpoints/<workspace-fingerprint>/<checkpoint-id>/`, where the fingerprint is the SHA-256 of the canonical workspace path. Storage uses atomic metadata replacement, restrictive permissions where supported, hash-validated preimages, and bounded sizes.
- **Checkpoint storage is link-proof and containment-checked on every operation.** Every path under the checkpoint root is validated with no-follow semantics: each component is lstat-checked for symlinks, the leaf must resolve canonically to its logical location (rejecting junctions and reparse points on Windows, and any link inserted after startup), and the root itself must remain a non-link directory outside the workspace. Metadata and preimage paths cannot be redirected to shared or attacker-selected paths.
- **Every approved mutation automatically creates a checkpoint.** After approval, under the mutation lock, after revalidation, the tool durably records the before-state (exact bytes for update/delete; absence for create) and the expected after-state with `state=prepared`, then applies and verifies the mutation, then finalizes to `state=applied`. If checkpoint storage fails, the mutation does not happen. If finalization fails after a successful apply, the result reports an uncertain recovery state instead of claiming success. The original edit approval covers checkpoint recording — no second prompt.
- **Crash reconciliation resolves `prepared` and `applied` checkpoints at startup.** `prepared` checkpoints are classified by comparing the current file state with the recorded before and after states: before wins → `abandoned`; after wins → `applied`; neither → `uncertain`. Siralos never guesses, never auto-modifies the workspace, and `/undo` refuses uncertain checkpoints. An `applied` checkpoint whose file matches the recorded before-state is classified `undone`: that is the recoverable undo-commit window (a crash between the destructive restore and the state update), and the classification is safe because the file is already at the pre-mutation state.
- **Undo restores only Siralos-owned changes, hash-checked.** `/undo` (latest eligible checkpoint) and `/undo <checkpoint-id>` require a complete reverse diff, one-time approval, and an exact match of the current file state against the checkpoint's recorded post-state, revalidated after approval and immediately before the destructive commit. A user or external change after the Siralos mutation is a conflict, never an overwrite; there is no force undo, no redo, and no conversation rewind. Restore reuses the mutation lock, path containment, protected-path checks, symlink checks, the safe-replacement primitive, and post-write verification — the undo-delete and undo-create branches use the same parent-chain identity verification and handle-identity proof as the create tool, and every commit/rollback of the restore uses the absence-preserving exclusive hard link, so a target that appears after displacement is never overwritten (rollback conflicts return an explicit uncertain result preserving the quarantine), and marks the checkpoint `undone` after verification even if cancellation arrives after the destructive commit point.
- **Retention is conservative, fail-closed, and not provider-configurable**: up to 100 checkpoints or 100 MiB per workspace; the 100 MiB limit measures the total actual regular-file bytes beneath the workspace's checkpoint directory, including every `metadata.json` and `preimage.bin` byte (filesystem allocation overhead is outside this logical byte limit), metadata-declared lengths are never trusted as disk accounting, and the proposed checkpoint's exact serialized metadata and preimage bytes are counted before any write; automatic pruning is DISABLED — reaching the count or byte limit (or failing to prove capacity through a truncated or expired enumeration, because any checkpoint's metadata or preimage is missing, unreadable, invalid, oversized, linked, or size-inconsistent, because a declared preimage's actual bytes do not match the metadata byte length or SHA-256 (a same-size corrupted preimage makes capacity unverifiable; file size alone is never treated as proof of content), because a declared preimage's filesystem identity or content state does not match the inspected object (verification is handle-bound: the pathname is lstat'd, opened read-only with `O_NOFOLLOW` where available, and a pre-read/final stability snapshot — `dev`, `ino`, `size`, `mtimeNs`, `ctimeNs` (bigint) — is captured from the opened handle before any byte is read and re-verified after the bounded read loop, requiring the handle and a fresh path lstat to remain the same non-link regular file with identical size and mutation timestamps — so a same-content hard-link, rename, symlink, or junction replacement and a same-inode in-place rewrite during verification are substitutions and are refused, and restoring `mtime` cannot hide a changed `ctime`; on Windows the identity/stability comparisons carry the binding because `O_NOFOLLOW` is unavailable, and unusable identity or stability fields fail closed; this detects mutation between the pre-read and final snapshots, never atomic protection against modification after final verification), or because content beyond the exact `metadata.json`/`preimage.bin` layout — unknown files, nested directories, temporary files, case-variant duplicates, links, special files — is present) refuses checkpoint creation with a typed storage-limit error before any write; unexpected content is never repaired, renamed, truncated, or quarantined, and the store never deletes any checkpoint or filesystem entry; no checkpoint entry is skipped during retention; existing checkpoints are preserved for manual inspection. Configured preimage limits are capped at `MAX_SUPPORTED_PREIMAGE_BYTES` (64 MiB): larger configured values are rejected at store creation, never silently clamped, so an unchecked configuration value can never drive a proportional allocation (the verifier materializes at most the cap plus one byte). Reading is a bounded loop with an explicit offset — a short read is never treated as EOF; reading continues until EOF, the bound, cancellation, deadline expiry, a read error, or an identity mismatch, with cancellation and deadline checked between reads. The capacity check-to-write sequence is not atomic against a same-user process modifying the checkpoint tree concurrently (Node offers no directory-relative primitive): no atomic global quota enforcement is claimed.
- **Checkpoint operations are bound to their before/after existence states.** One shared validator enforces, for prepared records and stored metadata alike, that `create` records an absent→present transition, `update` a present→present transition, and `delete` a present→absent transition — the operation-state relationship is the canonical invariant, never inferred from tool names. Any other combination (for example a create checkpoint carrying a preimage, or a delete without one) is refused: prepared records fail before any write, approval, or capacity inspection, and historical metadata failing the invariant fails closed as unverifiable capacity — it is never repaired or deleted, `get()` never returns it as valid, and reconciliation skips it safely.
- **Checkpoints contain local source-code copies.** Preimages may be source code; they stay on the local machine, are never sent to providers, never appear in workspace search, are never listed through `/checkpoints`, and never leave the checkpoint store.
- **Redo, conversation rewind, and Git staging/commits are deferred.** Undo is strictly one-shot per checkpoint; automatic Git commits are a separate later decision.

## Consequences

Positive:

- Mutations gain a durable recovery record and the user gains a safe, approval-gated undo path that provably cannot overwrite newer work — once mutations are offered (they are intentionally unavailable at this stage; see the status note above).
- Git inspection is a narrow, testable surface with mechanical enforcement of its boundaries (only the sandbox backend executes the Git process; providers and the CLI never parse raw Git or restore files).
- The sequence toward development commands stays conservative: approved mutations → Git inspection + checkpoints + undo → sandboxed commands → Godot.

Negative:

- Checkpoint storage duplicates file content locally (up to the documented limits); Windows mode bits alone do not provide equivalent ACL enforcement to POSIX owner-only permissions.
- Undo conflicts are strict by design: any later change to the file makes undo refuse to run rather than risk overwriting work.

Platform limitations:

- Restore and undo-delete commits use the shared safe-replacement/deletion primitives: the target is always displaced to a same-directory quarantine, the displaced object is hash-verified against the recorded post-state, and only then is the restore rename or unlink performed — on every platform, never only after a direct rename fails. Undo-create uses exclusive creation with a canonical-location check. The quarantine copy is never removed before the restored content is verified and the checkpoint is durably marked undone, and an uncertain state reports the recoverable quarantine path. None of this executes at this stage: `/undo` fails closed as `unavailable` (Node offers no directory-relative primitive).
- The Git adapter executes Git only through the sandbox backend (no shell, sanitized environment, bounds, timeout, cancellation, confined process tree, network denied, writes limited to the exact private run directory, host reads limited to the repository root and Git runtime roots). On hosts without an enforcing backend — for example Windows, where the pinned runtime cannot express the host-read allowlist — Git inspection reports unavailable and Git is never spawned. At this stage Git inspection is unavailable on every host: the adapter requires Siralos-owned private run directories for every invocation, and run-directory creation and cleanup fail closed (no directory-relative or delete-by-handle primitive).
